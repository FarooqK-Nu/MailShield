# Test and evaluation report

Status at the end of Phase 7. Every statement below was checked against test output unless it is marked "not verified".

## 1. How to run

```bash
npm run check           # typecheck, lint and all unit and integration tests
npx tsx tools/evaluate.ts --split dev      # regenerates fixtures/evaluation/dev.json
npm run test:e2e        # Playwright (sanitized preview, no outbound request)
```

On the Windows development machine, run the tests from `D:\` in PowerShell (see the notes in `docs/report.md`). Result at the end of Phase 7: 33 test files, 400 tests pass; typecheck, lint and `npm audit` are clean.

## 2. Evaluation

**Corpus.** 44 synthetic fixtures (`fixtures/labels/*.json`, generated by `tools/gen-fixtures.ts` and `tools/gen-eval-fixtures.ts`): 28 development, 16 held-out. Categories: legitimate 10, impersonation 12, tampered 8, ambiguous 8, edge cases 6 (forwarding, key rotation, outsourced sender, shared name, partial body coverage).

**Ground truth.** Each label has a `truth` (legitimate, suspicious or unknown) set when the fixture is built, separately from the `expected` snapshot used by regression tests. The evaluation compares the engine's answer with `truth`, so a disagreement is a finding, not a failed test.

**Method.** "Flagged" means the verdict is possible impersonation or authentication concern; "cleared" means no concerning mismatch; "abstained" means identity unverified. Precision and recall use only legitimate and suspicious messages. Recall counts an abstention on a suspicious message as a miss. Ambiguous messages are reported separately as an abstention rate. Rules were not changed during Phase 7: no thresholds were tuned, and the held-out set was run only to produce `fixtures/evaluation/heldout.json`.

| Set | Precision | Recall | F1 | Abstention on ambiguous | Overall abstention |
|---|---|---|---|---|---|
| Development (28) | 100% (9/9) | 69.2% (9/13) | 0.818 | 71.4% (5/7) | 32.1% (9/28) |
| Held-out (16) | 100% (5/5) | 71.4% (5/7) | 0.833 | 80.0% (4/5) | 37.5% (6/16) |

**Disagreements (all of them, from the generated files).**

- Missed by abstention (suspicious, verdict "identity unverified"): `brand-dmarc-unaligned`, `reply-to-divergence`, `link-mismatch`, `globex-link-mismatch` (development); `forged-auth-results`, `globex-reply-to-divergence` (held-out). These are by design: a Reply-To divergence, a link mismatch or a missing signature is shown as a finding but, on its own, does not move the verdict to a concern (`architecture.md` §3.9; invariant 10, no accusation from a single heuristic).
- Concern raised on a case that cannot be judged: `forwarded-list-footer`, `forwarded-subject-prefix` (a mailing list changes a signed message, so DKIM fails; failure alone cannot tell this from tampering) and `shared-personal-name` (rule R2 sees a trusted person's name on an unregistered address). The messages shown to the user describe a concern and its cause, not fraud.
- False positives on legitimate fixtures: none. False negatives (suspicious messages cleared): none.

**Limits.** All messages are synthetic and mostly built by the same author as the rules, so the figures describe this set only, not real mail. The sets are small (13 and 7 suspicious messages), so differences of a few percent are one message. No authorised real messages were available and none are included. The development and held-out fixtures were written by the same person at the same time, so the split guards against tuning, not against shared blind spots.

## 5. Hardening review

- **Fuzzing** (`packages/engine/test/fuzz.test.ts`): seeded random bytes, mutated valid messages, nesting beyond the limit, more parts than the limit, huge and numerous headers, unterminated quoted names and hostile DKIM tags. Every case ends in a result or the typed `AnalysisError`, each in under a few seconds. This is a bounded, seeded test, not a long fuzzing campaign.
- **Dependencies:** `npm audit` reports 0 vulnerabilities; CI now fails on high-severity advisories.
- **Extension permissions:** `sidePanel`, `identity` and `storage`; host access only to `gmail.googleapis.com` and the local service; scope `gmail.readonly`. No change was needed.
- **Copy:** automated scan plus review; no occurrence of "safe", "scam", "fraud" or similar in user-facing text.
- **Accessibility** (reviewed in source, not with a screen reader): focus ring already global; two spinners were not covered by reduced motion and now are; the evidence-trail replay now shows every stage at once when the user prefers reduced motion; the new Evaluation page uses real tables, headings and labelled controls. Not verified: contrast ratios were not measured and keyboard navigation of every page was not walked through in a browser.

## 6. Not verified or not done

- No automated test drives the Evaluation page in a browser (the route and the data are tested; the page type-checks and builds).
- The extension end-to-end test with a mocked Gmail API (decision A-12) is not done; the extension logic is covered by Vitest, including a test that the OAuth token goes only to the Gmail API.
- Live Gmail, opaque S/MIME, RSA-PSS and ECDSA signatures and real-client S/MIME messages are untested.
